# 防踩坑指南（活文档）

> **维护规则：每踩一个新坑，当场在本文件对应分类追加一条**（模板见文末），解决了就补全「解法」。
> 本文件是全项目唯一的坑集中地——`docs/开发指南.md` 只留指针，历史细节在 `docs/history/`。
> 编号规则：`构` 构建/打包 · `服` serve.py/架构 · `页` 网页 JS · `安` 安卓/WebView · `网` 网络/鉴权/部署 · `平` Windows 平台 · `测` 数据/测试 · `工` AI 协作工具

## 一、构建与打包（构）

**构1 · exe 命令行参数无效（最坑）**
症状：`--prepare-share` 等参数在 exe 上完全无效，照常解析+起服务。
根因：打包入口是 `bidking_launcher.py`，不是 `serve.py` 的 `__main__`；只写一处的参数 exe 永远执行不到。
规则：**新增命令行参数，`serve._handle_cli_args()` 和 launcher `main()` 两处都要接**。

**构2 · 打包报 PermissionError**
症状：构建部署时拒绝访问。
根因：正在运行的 `BidKing解析器.exe` 锁定文件。
规则：打包前 `taskkill //F //IM "BidKing解析器.exe"`（文件覆盖通常能成功，但干净状态最稳）。

**构3 · APK 漏 Kotlin 插件**
症状：APK 构建"成功"但一启动闪退 `ClassNotFoundException`。
根因：`build.gradle` 缺 `kotlin-android` 插件与 kotlin-stdlib。
规则：新建安卓工程核对插件三件套；构建成功 ≠ 能运行，必须真机/模拟器启动验证。

**构4 · 中文路径构建 APK 失败**
症状：`project path contains non-ASCII`。
解法：`gradle.properties` 加 `android.overridePathCheck=true`。

**构5 · R8 缺失类报错**
症状：`:app:minifyReleaseWithR8 FAILED`，提示 Missing classes（如 Tink 引用的 `javax.annotation.*`）。
解法：把 `app/build/outputs/mapping/release/missing_rules.txt` 的 `-dontwarn` 规则追加进 `proguard-rules.pro`。

**构6 · APK 签名不一致无法覆盖安装**
症状：`INSTALL_FAILED_UPDATE_INCOMPATIBLE`。
根因：换了签名密钥。规则：统一用 `bidking-release.keystore`；**keystore 丢失 = 所有用户永远无法升级，必须单独备份**。

**构7 · 价格配置种子被启动解析覆盖（测试时）**
症状：手工构造的 result.json 在测试实例启动后变回真实数据。
根因：launcher 启动即解析真实日志并重写 result.json。
规则：测试实例**先启动、等解析完成、再灌测试数据**。

**构8 · 打包备份产物 `.exe.bak` 险些入库（真实发生）**
症状：`git add -A` 后发现 `BidKing解析器.exe.bak`（build_nuitka.py 部署时把旧 exe 改名让位的备份）进了暂存区。
根因：`.gitignore` 只有 `*.exe`，不匹配 `.exe.bak` 结尾。
规则：`.gitignore` 已补 `*.bak/*.new/*.tmp`；**每次提交前 `git status --short` 扫一眼产物类文件**，别无脑 `add -A`。

**构9 · 不知道之前用哪个 Python 打包；批量探测 Nuitka 还会误报"没装"（2026-08-30 踩坑）**
症状：①隔一段时间要重打包，`python src/build_nuitka.py` 报找不到 nuitka 模块，翻开发指南只看到占位符「`<你的 Python 3.10+ 路径>`」，不知道原来用的哪个环境；②写脚本批量探测"哪些 Python 装了 Nuitka"，明明装了却全部判定为没装，差点重装一遍。
根因：①具体解释器路径含 Windows 用户名，属**本机信息**，不便写进会开源的文档，于是文档里只留了占位符；②glob 返回的路径混用 `/` 与 `\`（形如 `.../python/envs\default\Scripts\python.exe`），直接交给 subprocess 执行 `import nuitka` 会失败，被脚本一律归因为"没装"。
解法：①用 `BIDKING_BUILD_PYTHON` 环境变量指定构建解释器（`build_nuitka.py` 已支持，测试仍用 `sys.executable`）；②**本机具体路径记在 `.workbuddy/memory/`（不入库）**，文档只写通用约定；③探测脚本拿到候选路径先 `os.path.normpath()` 归一化，且**把非 0 返回码的 stderr 打出来**看真实原因，不要静默判否。
规则：①任何本机绝对路径都不许写进会开源的 md；②**宁可多花 10 秒手工 `python -m nuitka --version` 确认，也别信批量探测脚本的沉默结论**；③Nuitka 的 MinGW 工具链缓存在 `%LOCALAPPDATA%\Nuitka`（几百 MB，别删，删了要重下）。

## 二、serve.py / 架构（服）

**服1 · exe 与源码行为不一致**
症状：源码直跑正常、exe 不生效（或反之）。
根因：`serve.py` 的 `__main__` 不是 exe 的执行路径。
规则：任何"入口/初始化"逻辑改动，先确认 launcher 路径也覆盖。

**服2 · 类内调用模块级函数写成 `self.xxx()`**
症状：`AttributeError`。
规则：`_host_ok(self)`、`_peer_class(self)`、`_request_token(self)` 等是**模块级函数**，第一参数显式传 self。

**服3 · 改密码不清旧令牌**
症状：改密后旧令牌仍有效至过期。
现状：`/api/pass-set` 成功即清空全部令牌（已修）；新增"改安全状态"逻辑时记得评估令牌失效范围。

**服4 · 安全状态变更不考虑令牌失效范围**
规则：凡改密码/撤销设备/改开关，同步考虑：哪些已签发令牌需要立即作废（`_AUTH_TOKENS`）。

**服5 · 敏感静态文件裸奔**
症状：`result.json`（全部战绩）公网无需任何凭据即可下载。
根因：GET 鉴权白名单把所有非 `/api/` 路径都放行。
规则：**新增数据类静态文件时必须评估公网可见性**；`result.json/silver_cache.json` 对 public 需令牌（已有），新文件照此办理。

**服6 · 巨石文件谨慎重构**
现状：`serve.py` ~3000 行、`bidking_report.html` ~4000 行、`MainActivity.kt` ~2300 行。
规则：功能活跃期**不做**大重构；改动小步提交 + 跑回归。

**服7 · 大日志全量整读拖慢启动（2026-08-31）**
症状：`Player.log` 涨到 5.2GB / 1700 万行后，双击 exe「正在解析…」要卡 1 分钟；根因之一是 `extract_inventory` 每次 `fp.read()` 整个日志再全量正则扫描。
解法：引入 `inventory_cache.json`（与日志同目录，仿 silver_cache 范式）：按「日志文件大小 log_size + 上次扫描偏移 tail_offset」增量——log_size 未变→零 IO 复用缓存；变大→seek 到上次偏移只扫新增尾部；变小（日志被游戏清空/重置）或缓存损坏→全量重扫重建。合并语义不变：按事件 offset 排序、后出现覆盖先出现。
规则：**任何"扫大日志"的解析都要带增量缓存，禁止整读**；新增缓存前先看 silver_cache 范式；缓存必须带版本号与 log_size 校验，损坏自动回退全量。

## 三、前端网页 JS（页）

**页1 · 一处 JS 语法错 = 全页按钮报废**
症状：页面所有点击无反应。
根因：单 `<script>` 块约 11 万字符，一处语法错整块不执行。
规则：改 html 后必过 `node --check`（打包流程已内置）；已有语法检查前手动提取检查。

**页2 · 弹窗 DOM 在 `<script>` 之后**
症状：`getElementById` 拿到 null、绑定失败、点击无反应。
规则：弹窗等关键 DOM 必须在脚本块之前（本项目已整改，新增弹窗遵守）。

**页3 · Proxy 包装浏览器原生对象必须补 `get` 陷阱**
症状：`Illegal invocation`，且异常常被上游 try/catch 吞掉，表现为"图全没了/莫名没内容"。
根因：Web IDL 方法校验 `this` 内部槽位，Proxy 不是平台对象。
规则：`get` 陷阱把方法 `bind` 回 target（canvas 字体放大已有实现，照抄）。

**页4 · 移动 DOM 节点会清空 canvas 位图**
症状：切换图表后内容被拉伸/挤压（旧位图塞进新宽度）。
根因：`anchor.before(section)` 移动节点 → canvas 位图重置，且显示后未按新宽度重绘。
规则：**显示/移动 canvas 后，必须强制按容器 `clientWidth` 重设 `cv.width/height` 再重绘**（`showChart` 已实现，改动时保留该步）。

**页5 · 像素抽样判断"画没画出来"不可靠**
症状：三合一图表回退"三张全显"且永不恢复，用户看到"三合一被拆开"。
根因：细线条图表按 `p += 400` 抽样会漏检所有线条 → 误判空白 → 兜底回退 → 旧逻辑一旦回退永久锁定。
规则：**图表合并/收起逻辑以数据在场为准（`report.games.length`），像素抽样只作辅助**；任何兜底状态必须可自动恢复，禁止"永久锁定"。

**页6 · 生命周期：先显示后绘制，防"图全没了"**
规则：显示图表 → rAF 重绘 → 再隐藏其他张（顺序不能反）；隐藏态 canvas 宽度为 0，显示后必须按真实宽度重设再画。

**页7 · 数据晚到竞态**
症状：页面渲染时数据还没 fetch 完 → 空态/图缺失。
规则：数据晚到的自愈已覆盖（`scheduleEnsure` 轮询重画 + 拉取耗尽触发重新加载）；新增异步渲染逻辑时要考虑"数据比代码晚到"。

**页9 · 表格标签补挂「行数相同就跳过」→ 重渲染后标签消失（用户实测踩坑）**
症状：卡片/表格的字段标签（时间/地图/赢家…）在页面自动刷新重渲染后整排消失，布局本身不变。
根因：TABLE_LABEL_JS 的 mark() 有「data-label 已挂且行数相同就 return」的省略判断——自动刷新重渲染后行数往往不变 → 跳过补挂，新单元格没有 data-label，td::before 全空。
解法：去掉跳过判断，观察到的变更一律全量重标注（页面行数少，开销可忽略）。

**页10 · 软刷新替代 reload() 时必须存取滚动位置**
症状：exe 端解析完成后 App 页面数据更新，但滚动位置跳回顶部（用户明明在看第 50 行）。
根因：整页 `wv.reload()` 天然丢滚动位置；改成调页面函数软刷新（`window.render("result.json")`）后，render 重建表格 DOM，`window.scrollY` 与 `.table-wrap` 的 `scrollTop` 仍会归零。
解法/规则：**凡绕过页面自身流程直接调 render()，前后必须存取 `window.scrollY` + 所有 `.table-wrap` 的 `scrollTop/scrollLeft`，并在 `requestAnimationFrame` 里恢复**（见 MainActivity.kt 注入脚本 softRender；缓存渲染同理）。

**安14 · 固定高度卡片 + 溢出裁剪会裁掉行内按钮（用户实测踩坑）**
症状：生涯卡片「拍下物品」按钮边缘被裁掉一点，看起来不完整。
根因：卡片固定高度 + overflow hidden，行内按钮（含文字基线空隙）比预留空间高出几像素就被裁。
解法：卡高预留余量（86→92，虚拟滚动步长 CARD_H 同步 92→98）、交互单元格 overflow visible、按钮紧凑化（min-height 0 / 小 padding）。改卡片尺寸时**虚拟滚动步长必须同步改**。

**页8 · 拿仓率等文本挤压**
症状：小屏幕统计卡文字压缩。
规则：App 模式统计卡用紧凑网格样式（`__bk-compact` 已实现）；新增卡片注意小屏字号。

## 四、安卓 App / WebView（安）

**安1 · 令牌竞态：页面先请求、令牌后注入**
症状：局域网+已设密码时，生涯/道具/价格库全部"没数据"、401；无密码实例永远测不出（见测4）。
根因：App 在 `onPageFinished` 才注入令牌，页面 `DOMContentLoaded` 就发数据请求。
解法：**双保险**——①连接成功即把令牌写 WebView Cookie（服务端认 Cookie，首请求即携带）；②报表页 `waitForAppToken` 等注入就绪再拉数据。**新增页面/接口沿用 Cookie 通道，不要新发明注入时序。**

**安2 · 函数直接当事件处理器，事件对象被当业务参数**
症状：生涯页"当前[object PointerEvent]显示 0 场"。
根因：`reloadBtn.addEventListener("click", loadCareerData)` —— `loadCareerData(uid)` 收到的是事件对象。
规则：**带参函数挂事件必须包箭头函数**：`addEventListener("click", () => loadCareerData())`。

**安3 · CSS 整体隐藏父容器连坐珍贵内容（史上最坑）**
症状：App 模式页面"空白"。
根因：`#ctrlPanel{display:none}` 把统计卡片一起藏了（卡片物理上在面板里）。
规则：隐藏父容器前必须确认内部内容；本项目只藏 `#ngrokRow` 等具体行。

**安4 · 底部功能栏遮挡页面内容**
症状：页面最底部文字被压住。
规则：改 `funcBar` 可见性一律走 `updateFuncBarVisibility()`（内部自动重算 webHost padding）；padding 重算用双 `post` 等 measure。

**安5 · 生涯页虚拟滚动被卡片化破坏**
症状：生涯明细只显示约 18 局。
根因：对 `#careerTableScroll` 设 `overflow:visible` 破坏虚拟滚动的滚动容器。
规则：卡片化 CSS 不得作用于虚拟滚动容器。

**安6 · Material3 主题把 Button 撑大**
症状：小按钮尺寸失控、标题截断。
规则：精确控尺寸用 `TextView` + 自绘 `GradientDrawable`，不用 `Button`。

**安7 · `window.open` 在 WebView 静默失效**
症状：点"生涯/道具"按钮无反应。
解法：注入 JS 覆盖 `window.open` 为当前页跳转（已实现）。

**安8 · 页面通知需要 Android 13+ 运行时授权**
规则：低库存通知有权限引导流程（notifyGuideModal），不要假设已授权。

**安9 · APK 反编译防护**
现状：R8 混淆+资源收缩已开启（v1.1，5.4MB→1.78MB）；App 无内置秘密（令牌运行时换取）。
规则：开 R8 后**必须真机/模拟器回归**（WebView 注入、加密存储、通知）；R8 缺类按构5处理；不加第三方加固壳（杀软误报 + 兼容性风险）。

**安10 · ngrok 免费版警告页劫持「注入前首请求」（用户实测踩坑）**
症状：App 经 ngrok 打开道具页显示「无法连接价格数据库」，局域网正常；生涯页偶发首屏失败。
根因：ngrok 免费版对「浏览器 UA + 无 `ngrok-skip-browser-warning` 头」的请求回 **200 + HTML 警告页**；App 的 fetch/XHR 包装器原来在 `onPageFinished` 才注入，页面 `DOMContentLoaded` 的首请求赶在注入前出去 → 拿到 HTML → `response.json()` 抛异常。页面无重试 → 一次定生死。
解法：①包装器注入提前到 `onPageStarted`（页面脚本执行前，onPageFinished 兜底注入幂等）；②页面侧 `fetchJsonRetry`（3 次、1.5s 间隔，非 2xx/JSON 解析失败都重试）双保险。**新增页面一律用重试拉取，别裸 fetch 一次定生死。**
实证：`curl -A "<WebView UA>" https://xxx.ngrok-free.dev/api/item-prices` 无 skip 头 → 200 text/html 2.8KB 警告页；带头 → 正常 JSON。

**安11 · App 与页面的盈亏配色语义颠倒（用户实测踩坑）**
症状：App 顶栏显示「红盈」时页面盈亏数字/拿仓行背景全是绿的；切到「绿盈」反而变红——用户以为「拿仓背景不跟配色走」。
根因：两层叠加。①页面 CSS 权威语义是 `normal=绿盈红亏、inverted=红盈绿亏`（exe 报表页按钮按此标注），而 App 的按钮文案映射写反（inverted 显示「绿盈」）；②App 的 `injectGlobalTheme` 只持久化主题 key、**没持久化配色全局 key**，页面自身启动读全局 key（空→normal）先按默认上色，属性注入只是事后补救。
解法：①`injectGlobalTheme` 同步 `localStorage.setItem('bidking-global-profit-colors', pc)`；②按钮文案改为 `if (profitInverted) "红盈" else "绿盈"`（与页面 CSS 语义对齐）；③CAREER_ENHANCE_JS 兜底重读全局 key 应用。**两端共享的语义（模式名/键名/默认值）改动前先对照 exe 页面的按钮标注，别凭注释猜。**

**安13 · 系统 Toast 图标回落默认机器人，与应用图标无关（实测踩坑）**
症状：Android 12（MuMu 模拟器实测）的 Toast 左上角图标永远是「蓝色机器人蓝图」默认图，换任何应用图标（位图自适应图标、关闭 arsc 资源优化）都不变；而启动器上应用图标正常。
根因：Android 12 的 Toast 模板由 SystemUI 渲染，图标走「跨进程按资源 ID 加载应用 drawable」，部分系统 UI 实现上这条路径会失败并回落 `sym_def_app_icon`（蓝图机器人）——应用侧无法控制。
解法：**前台自绘 Toast**（Android 11+ 只禁「后台」自定义视图 Toast，前台合法）：自建布局（应用图标 mipmap + 文本，深色圆角药丸背景），`toast.setView(...)` 展示，全部入口统一走 `toast()` 助手；失败兜底退回系统 Toast。实测 MuMu 上图标与应用完全一致。通知小图标另用单色镂空品牌矢量（ic_stat_crown），系统要求单色不能用彩色位图。

**安12 · 拿仓行底色三连败：卡片化 CSS、时序守卫、假验证（用户三次反馈才修对）**
症状：App 生涯明细的拿仓对局始终没有配色底色，连修三版（v1.5/v1.6）都无效；桌面浏览器却正常。
根因：三层叠加，每层都能单独杀死底色——
①页面自带 App 卡片化 CSS：`html.app-mode #careerTableScroll table tbody tr { background:var(--panel) }`（ID 特异性）盖过页面本体 `tr.win-positive { background:var(--profit-good-bg) }`（无 ID）；
②App 增强注入的表格化规则 `...tbody tr { background:transparent !important }` 同样带 ID+!important，压过一切不带 ID 的行背景规则（含第一版注入修复）；
③把修复规则放进 `CAREER_ENHANCE_JS`，而它开头 `if (secs.length < 3) return` 时序守卫**可能整块不注入**——守卫没过时页面回落到①的卡片渲染，规则从未生效。两种渲染（卡片/表格）还会随注入时序随机切换。
解法：拿仓底色规则放进 `injectTouchFeel`（**无条件注入、无守卫、幂等**的样式表），规则带 `#careerTableScroll` ID + `.win-*` 类（特异性 1,2,4 > 两个对手的 1,1,4），深浅主题 × 配色方案定向取值，卡片/表格两种渲染通吃。
教训：①**验证必须像素取样**（PIL 读 screencap 的实际 RGB），肉眼看缩略截图会把 10% 透明度脑补成"生效"；②往已有样式表加规则前，先 grep 同文件里所有同选择器前缀的 `!important` 规则（尤其带 ID 的）；③带时序守卫的注入块里不要放「必须生效」的规则。

**安15 · 看门狗轮询的提前 return 必须同时「停表 + 复位 UI」（用户实测踩坑，v1.11 修）**
症状：点过「启动估价器」后，App 切后台再回来，状态栏永久卡在「启动中：idle」，把「已连接/连接失败」全盖住，看起来像连不上，只能彻底退出 App 才恢复。
根因：`checkLaunchStatus` 开头 `if (activeUrl.isEmpty() || authToken.isEmpty()) return@Thread` —— 直接 return，**既不停看门狗也不恢复状态栏**；而看门狗 Runnable 每 5 秒无条件重排（4 分钟才自停），且每轮把状态栏写成「启动中：idle」。令牌在切后台/重连时被清空后，所有检查都走这个 return 分支 → 死循环霸屏。
解法/规则：**凡周期轮询类逻辑，任何「提前退出」分支都必须走统一的 stopWatchdog()：停标志位 + removeCallbacksAndMessages + UI 复位**。状态栏拆「连接层/启动层」两层由 renderStatus() 统一渲染，启动层 90 秒无更新自动作废交还连接层；`state == "idle"` 连续 2 轮即判定启动尝试结束，不再空转 4 分钟。

**安16 · 多服务器场景令牌必须按服务器 URL 隔离（v1.11 修）**
症状：两个解析工具 tab 来回切，每次都要重新连接；快切时偶发页面全空 401。
根因：`authToken` 是单一全局变量——切 tab 就被新服务器覆盖；令牌也不持久化，进程被系统回收即丢，回前台只能整个重走登录（密码/配对挑战）。
解法/规则：令牌容器改 `tokenMap[normalizeServerUrl(url)]` + EncryptedSharedPreferences 加密落盘（`tok_<url>`）；`authToken` 降级为只读派生属性 `get() = tokenFor(activeUrl)`，25 处读取点零改动，只改赋值点；**`injectTokenIntoPage(wv, viewUrl)` 必须按这张 WebView 自己的 URL 取令牌**，不能用 activeUrl（切 tab 秒显时页面还属于旧服务器，串号即全页 401）。续连校验用 `/api/status`（走令牌拦截），不能用 `/api/server-info`（免鉴权白名单，拿它校验等于没校验）。

**安17 · 注入的 fetch 缓存层必须排在令牌包装器之后（v1.11）**
症状：报表页本地缓存层若先于令牌包装器注入，它捕获的 `origFetch` 不带 `X-Auth-Token` → 后台对账请求 401 → 永远「暂时连不上电脑」。
根因：缓存层的 `origFetch = window.fetch` 在注入瞬间固化，包装顺序错了就固化错。
规则：注入顺序必须是 injectTokenIntoPage → injectReportCacheLayer（onPageStarted 里已按此顺序）；新增任何再包 window.fetch 的层，都要想清楚它捕获的是「哪一层」的 fetch。另外：注入 JS 贴进 Kotlin 原始字符串前先单独存 .js 过 `node --check`，正则里的 `$` 在 Kotlin raw string 会触发模板插值，改用 indexOf 写法。

## 五、网络、鉴权与部署环境（网）

**网1 · 局域网信任、公网严格的分级不能混**
现状（2026-08-29 用户决策）：local 全权；lan 视同本机（未设密码免鉴权/设密码凭令牌）；public 走完整链（密码+配对+令牌）。
规则：改鉴权先读 `docs/api-contract.md` 鉴权矩阵；**新增接口必须落到矩阵里**。

**网2 · ngrok 转发流量在 TCP 层是 127.0.0.1**
症状：公网访客被当成"本机"全权放行（曾是真实漏洞）。
解法：`_peer_class` 在隧道运行时读 `X-Forwarded-For` **最右侧**一节（左侧可伪造）；无隧道/非回环对端一律忽略 XFF。
规则：新增"来源判定"逻辑必须经过 `_peer_class`，不要自己读对端地址。

**网3 · 令牌竞态在"无密码测试环境"测不出来**
症状：测试全绿、用户实测全 401。
根因：竞态只在"需要令牌"时暴露；测试实例没设密码 → 一切放行 → 盲区。
规则：**测试环境的密码/安全开关状态必须与生产一致**；关键流程用"设了密码的实例"过一遍。

**网4 · A/B 对比测试被环境污染**
症状：误判"R8 导致连不上"，实际是 exe 没开。
规则：A/B 前先确认**被测服务在线**（curl /api/ping）；结论与预期矛盾时优先怀疑环境。

**网5 · 大响应必须压缩**
症状：生涯全量 48MB JSON 经 ngrok 传几分钟，手机端超时/没数据。
解法：`_send_json` 对 >64KB 且客户端支持 gzip 的响应自动压缩（48MB→7MB）。
规则：新增大体积接口默认走 `_send_json`（自动获得压缩），不要手写响应。

**网6 · 令牌生命周期 = exe 进程生命周期**
现状：令牌在内存，exe 重启全失效；设备密钥持久化不受影响。
规则：凡"重启 exe 后 App 行为异常"类问题，先想到令牌失效；App 侧 Cookie/sessionStorage 的旧令牌会被新连接覆盖。

**网7 · 远程退出接口已停用**
现状：`POST /api/exit` 恒 403。规则：不要恢复它。

**网8 · 已配对设备重复配对 = 死锁（用户实测踩坑）**
症状：App 报「配对请求被电脑端拒绝（检查密码是否正确）」，且配对列表出现同一手机的多条记录；重新添加服务器后连不上、干等 3-4 分钟。
根因：服务端对已配对 device_id 直接 400「该设备已配对」，但 App 的设备密钥按**服务器地址字符串 hash** 存储——地址一变（ngrok 域名变化/重新添加时写法不同）密钥就查不到 → 想重新配对又被拒 → 死锁，只能电脑端手动撤销。错误信息还是误导性的「检查密码」。
解法：①服务端对已配对 device_id 凭**正确密码**直接自动重发密钥+令牌（`auto_paired`，人工同意这道关对该设备已过过一次）；②App 的 device_id 改用 ANDROID_ID（清数据/重装不变）；③App 透出服务端真实错误、`pollPairKey` 把 `already_paired` 列为快速失败态。落在 2026-08-30 提交（serve.py pair/request + MainActivity.kt）。

**网9 · 「仅本机」判定裸看 client_address（网2 规则的又一次违例）**
症状：test T19d 发现公网 ngrok 访客持任意有效令牌可读 `/api/pass-info`（密码启用状态+提示语）。
根因：pass-info 处理器自己用 `client_address == 127.0.0.1` 判本机，而 ngrok 转发流量 TCP 对端就是 127.0.0.1（同网2）。
规则：**一切来源判定只准调 `_peer_class`**；新增「仅本机」接口时对照 api-contract 鉴权矩阵写测试（公网+有效令牌必须 403）。

**网10 · 本机 `git push` 到 GitHub 连不上：443 被拦，22 通（2026-08-30 开源时踩坑）**
症状：`git push` 报 `Recv failure: Connection was reset` / `Failed to connect to github.com port 443 after 21034ms`；但**浏览器能正常打开 GitHub**。
根因：机器装了代理软件（注册表 `Internet Settings` 里 `ProxyServer=127.0.0.1:7892`）但 `ProxyEnable=0` 且代理软件没运行 → 命令行裸奔直连 → `github.com:443` 超时被拦。浏览器另有自己的通道，所以"浏览器能开 ≠ 命令行能连"。
诊断三步（别急着换工具）：① `curl -m 8 https://github.com` 判 https 通不通；② Python `winreg` 读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 看 `ProxyEnable/ProxyServer`（`reg` 命令被安全策略禁用，用 Python 读）；③ socket 分别探 `github.com:22`、`ssh.github.com:443`、`127.0.0.1:<代理端口>`。
解法：**改走 SSH**——实测 `github.com:22` 与 `ssh.github.com:443` 都通，而 443 的 https 不通。步骤：`ssh-keygen -t ed25519`（Git 自带 `C:\Program Files\Git\usr\bin\ssh-keygen.exe`）→ 公钥贴到 GitHub Settings → `git remote set-url origin git@github.com:<user>/<repo>.git` → push。首次连接用 `-o StrictHostKeyChecking=accept-new` 自动落 known_hosts。
规则：①**命令行网络问题先查系统代理开关**，不要一上来就怀疑仓库地址；②端口探测优先于换协议；③本机无 gh CLI、GitHub MCP 建仓库返回 **403 Resource not accessible by integration**（集成 token 无 repo 权限），**仓库只能网页手动建**，别在 MCP 上空转。

## 六、Windows 平台（平）

**平1 · 启动外部程序必须 `os.startfile()`**
症状：`subprocess.Popen` 启动的估价器约 60 秒后自杀（CTRL_CLOSE_EVENT）。
规则：拉起 GUI 程序一律 `os.startfile`。

**平2 · Tk 窗口后台按键要先发 `WM_SETFOCUS`**
症状：PostMessage 按键被 Tk 丢弃（0/3 成功）。
解法：`WM_SETFOCUS` + `WM_KEYDOWN` 定向投递（0.01 秒生效）；全局抢前台按键是最后手段且必须校验前台窗口。

**平3 · 判断外部程序存活不能看启动器 PID**
根因：启动器 exe → 真程序 两段式，启动器拉起后自退。
规则：按"程序所在目录下是否有活进程"判断（`process_pids_under_dir`）。

**平4 · exe 显示的进程数 ≠ 实例数**
现状：Nuitka onefile 是"引导进程 + 实际进程"两个同名的。
规则：判断多实例用端口监听/ping，不要数进程。

**平5 · 文件覆盖 ≠ 进程更新**
症状：新 exe 已落盘，运行中的实例仍是旧逻辑（改了等于没改）。
规则：**验证新代码前必须重启对应进程**；部署后 `taskkill` + 重新启动。

**平6 · 路径含中文+多级同名目录**
规则：读写路径用完整绝对路径（形如 `<你的项目盘>:\<项目目录>\...`），不用相对路径。

**平7 · 解析器退出后 ngrok 残留后台（用户实测踩坑）**
症状：直接退出 exe（关窗口/任务管理器强杀）后 ngrok 隧道仍在跑，公网入口继续开着；只有先在网页上点停止才干净。
根因：ngrok.exe 是普通子进程，Windows 父进程退出**不会**自动杀子进程；`terminate()` 清理只在优雅路径执行，强杀/关窗口根本走不到。
解法：spawn 后把子进程放进 **KILL_ON_JOB_CLOSE 作业对象**（`winlaunch.assign_job_kill_on_close`）——进程无论以何种方式终止，内核关闭作业句柄时连带杀掉 ngrok；`ngrok_start` 前再按映像名清一次历史孤儿（`winlaunch.kill_images(["ngrok.exe"])`）。**Windows 上「父死子随」只有作业对象一条可靠路径，atexit/信号处理在强杀路径下不可靠。**

**平8 · 「程序是否已运行」按目录扫描会扫到自己（用户实测踩坑）**
症状：把 BidKing解析器.exe 放进估价器同目录使用时，远程启动估价器永远不真正启动（走了「已在运行→置顶」分支），填绝对路径也没用。
根因：`process_pids_under_dir(估价器目录)` 按路径前缀匹配**任何**进程，解析器自身进程也在该目录下 → 自己把自己误判成「估价器已在运行」。
解法：扫描加排除参数（`exclude_names`=自身 exe 文件名集合、`exclude_pid`=os.getpid()）。注意 onefile 是引导+实际**双进程同名**，按 PID 排除排不掉另一个，必须按映像文件名排除；serve 侧统一走 `_estimator_pids()` 包装。
